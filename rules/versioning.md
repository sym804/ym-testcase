# 버전 관리 규칙

## 버전 체계: `system.feature.fix.patch`

| 자리 | 의미 | 변경 기준 | 예시 |
|---|---|---|---|
| **system** (A) | 대규모 변경 | 기술 스택 교체, UX 라이브러리 교체, 대규모 신기능. 연 0~1회 | 0 → 1 (오픈소스 정식 공개) |
| **feature** (B) | 리팩토링·아키텍처 변경, 신규 기능 추가 | 없던 것이 생길 때. 새 화면, 새 영역, 새 모듈 | 시트 트리, 커스텀 필드, 다국어 |
| **fix** (C) | 작은 기능 추가, 큰 버그 수정 | 기존 기능에 옵션이나 칸을 더하는 정도. 사용자가 기능을 못 쓰거나 보안 위험이 있는 오류 | 결과 저장 실패 수정, 필터 옵션 추가 |
| **patch** (D) | 마이너 버그 수정 | UI 텍스트, 스타일, 사소한 동작, 운영 영향이 작은 보정 | 라벨 오타, 색상 조정 |

상위 자리를 올리면 하위는 0 으로 초기화한다(1.0.1.1 -> 1.1.0.0).
동시 변경은 두 자리를 같이 올린다.

**리팩토링은 B 다. A 가 아니다.** 내부 구조만 바꾼 것은 아무리 커도 B 다.
모놀리스 분할이 B 의 상한선이다.

**기능 추가는 규모로 B 와 C 를 가른다.** 새 화면처럼 없던 것이 생기면 B,
기존 기능에 옵션이나 칸을 더하는 정도면 C 다.

> **fix vs patch 판단 기준**: 해당 수정이 없으면 사용자가 기능을 못 쓰거나 보안 위험이 있으면 `fix`, 불편하지만 기능 자체는 동작하면 `patch`.

## 릴리즈 노트 항목 분량 상한

올린 자리를 따른다. 이슈 블록을 포함한 값이다.

**세는 것은 `- ` 로 시작하는 항목 줄이다.** 제목 한 줄, "컴포넌트 버전" 표,
블록 헤딩(`### 이슈` 등)은 세지 않는다. 2026-09-18 실측에서 D 자리 절
v1.4.0.1 / v1.5.1.1 / v1.5.5.1 은 항목 4줄에 표와 헤딩까지 11~13줄이었다.
전체 줄로 세면 기존 절이 전부 위반이 되므로 항목 줄로 센다.

| 자리 | 상한 |
|---|---|
| A | 1,600자 |
| B | 1,200자 |
| C | 900자 |
| D | 5줄 |

수치는 남긴다. 도출 과정만 뺀다.

**번호를 다시 잡을 때 과거 절은 소급하지 않는다.** 릴리즈 노트 절과 커밋 메시지와
엑셀 `수정 버전` 이 그 번호로 이어져 있어 지금 바꾸면 세 곳이 갈라진다.
대신 재정의 사실과 기준을 릴리즈 노트 상단에 적는다.

## 컴포넌트별 독립 버전

```
YM TestCase System  (전체 릴리즈 태그)
├── Frontend       (UI/UX 변경, 페이지 추가, 컴포넌트 수정)
├── Backend        (API 변경, 비즈니스 로직, 보안 수정)
└── Database       (테이블/컬럼 추가·변경·삭제, 마이그레이션)
```

- 각 컴포넌트는 **독립적으로** 버전이 올라갑니다.
- System Version은 전체 릴리즈 단위의 태그 역할이며, 컴포넌트 중 하나라도 변경되면 함께 올립니다.
- 이슈 목록(Issue_list.xlsx)에는 **컴포넌트 버전**을 기록합니다 (시스템 버전 아님).

## 버전 변경 규칙

| 변경 대상 | 올리는 버전 | 예시 |
|---|---|---|
| Frontend만 수정 | Frontend + System | FE 로그인 버그 → FE fix +1, System fix +1 |
| Backend만 수정 | Backend + System | BE API 오류 수정 → BE fix +1, System fix +1 |
| DB 스키마 변경 | Database + Backend + System | 테이블 추가 → DB feature +1, BE 동반 수정 |
| 전체 변경 | 전체 | 대규모 기능 추가 |

## 버전 사본 위치

릴리즈 노트의 "현재 버전" 블록이 정본이고 아래 넷은 사본이다.

| 파일 | 축 | 비고 |
|---|---|---|
| `backend/main.py` 의 `version=` | Backend | |
| `frontend/package.json` 의 `version` | Frontend | |
| `frontend/package-lock.json` 의 `version` | Frontend | 자리가 둘. 최상위와 `packages[""]` |
| `frontend/src/i18n/ko/common.json`, `en/common.json` 의 `version` 문구 | System | 화면 푸터 |

**버전을 올린 다음에 `npm install` 을 돌린다.** lock 의 `version` 은 사람이 적는
값이 아니라 npm 이 그 시점 `package.json` 을 보고 박제하는 값이다. install 을
먼저 돌리면 옛 버전이 박제된 채로 커밋된다. 커밋 cfa6316(System v1.5.5.0)부터
v1.6.0.0 까지 lock 이 뒤처져 있던 원인이 이것이다(SYM-104).

사본을 늘리면 감시 밖이 생긴다. 새 사본을 만들 때는 대조 테스트에 케이스부터 붙인다.

```bash
python -m pytest backend/tests_unit/test_version_consistency.py -q
```

## 릴리즈별 컴포넌트 버전

**정본은 `Release_note.md` 각 절의 "컴포넌트 버전" 표다.** 여기에 표를 따로 두지 않는다.

예전에는 이 자리에 이력 표가 있었으나 사본이라 어긋났다. 2026-09-18 실측에서
릴리즈 노트 절 44개 중 22개가 표에 없었고, 남아 있던 22개 중 v0.5.0.0 의
Database 값은 릴리즈 노트와 다른 값(0.2.0.0 대 0.3.0.0)이었다. 불완전한 데다
부정확했다. 표에만 있고 릴리즈 노트에 없는 릴리즈는 0건이어서 지워도 잃는 것이
없다. 사본을 감시 밖에 두느니 사본을 없앤다(SYM-105).

특정 릴리즈의 컴포넌트 버전이 궁금하면 릴리즈 노트에서 그 절을 찾는다.

```bash
grep -A 10 "^## v1.5.5.0 " Release_note.md
```
